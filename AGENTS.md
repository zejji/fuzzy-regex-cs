# FuzzyRegex - working notes for agents

A .NET 10 port of [mrab-regex](https://github.com/mrabarnett/mrab-regex), the Python `regex`
module. The headline feature is fuzzy (approximate) matching with per-error-type budgets, which
no .NET library provides.

**Start every session by reading `docs/plan/STATE.md`.** It says what release is in progress, the
checklist of what is left, the rules in force and the next action.

## Tracking state and progress: the rules

Each kind of information has exactly one home. Never record it anywhere else, and never start a
new file to hold it.

| Information | Its only home | Who updates it, and when |
|---|---|---|
| Current status: the release in progress, its checklist (item, branch, state, what is left), rules in force, next action | `docs/plan/STATE.md` (one screen, 50 lines at most) | whoever changes an item's state, in the same commit or straight after |
| The plan: what each phase or release covers and why. No status | `docs/plan/ROADMAP.md` | when the owner changes scope; a numbered spec amendment goes with it |
| Decisions, the owner's included | `docs/plan/DECISIONS.md`, append-only dated one-liners | when the decision is taken |
| Defects: one row per root cause, with status | `docs/KNOWN-DEFECTS.md` | on every find, branch, fix and merge |
| Divergences from upstream | `docs/DIVERGENCES.md` and `docs/plan/upstream-reports/LEDGER.md` | when a divergence ships or is judged |
| Parity board | `docs/STATUS.md` | generated by `tools/check-ratchet.ps1`; never by hand |

Rules:

- **Status lives only in `STATE.md`.** Not in ROADMAP, not in a design note, not only in a session
  brief or a chat. If you finish, start, block or drop a checklist item, update `STATE.md`.
- **Do not create plan or status documents.** A dated file in `docs/plan/` (`2026-...md`) is a
  point-in-time record: a design, survey, measurement or review. It is linked from the checklist
  item it serves and is history, never the current plan. Mark one `Superseded` when it stops
  describing the work.
- **Scope changes only with the owner,** recorded in ROADMAP and DECISIONS on the same day, then
  reflected in `STATE.md`.
- **Session handovers** (`.claude/driver/next-session-brief-*.md`, or a Junie hand-back) say only
  what happened since the last session and point to `STATE.md`. They never replace it.
- **Scratch** (`.scratch/`) holds logs, run folders and working notes. Nothing there is status;
  anything a later session needs goes into the homes above.
- `docs/plan/slices/` is the phase 0-7 queue, kept as history. Work since 2026-10-16 is tracked in
  the `STATE.md` checklist and KNOWN-DEFECTS rows, not slice files.

## Checkpoint and resume

The owner should only ever need to say "continue". That works only if every session follows this.

**Resume** (on "continue", a new session, or after a context compaction):

1. Read `docs/plan/STATE.md`. Trust it over memory, chat history and session briefs.
2. Check its "In flight" block against reality: is each listed process still running (PID), what
   does its log say, is each listed uncommitted change still there (`git -C <worktree> status`)?
   Finish or clean up what has ended before starting anything new.
3. Act on any "Waiting on the owner" item the owner has answered; leave the rest waiting.
4. Do the "Next action". After it, the next one is the first checklist item that is not done and
   not blocked on the owner.
5. If STATE.md is missing, contradicts git, or names nothing to do, say so and ask. Never guess.

**Checkpoint**: rewrite STATE.md's "Updated" line, the item's row, "In flight" and "Next action":

- when a checklist item changes state (started, gate passed, blocked, merged);
- when a long job (a timing run, a sweep, a subagent) starts or ends: record its PID, log path
  and what to do with the result;
- at least every 30 minutes of work, and before ending a turn that leaves anything running;
- before stopping for any reason: a blocker, the owner's deadline, a low allowance.

A checkpoint also commits work in progress on its branch (a `WIP` commit is fine). It commits
STATE.md on main too. Work that cannot be committed yet is listed under "In flight" with its
worktree path.

**Never** keep status only in a chat reply, a session brief, scratch notes or memory. If it is
not in STATE.md, the next session does not know it.

## Orientation, in order

| File | What it tells you |
|---|---|
| `docs/plan/STATE.md` | status, checklist, rules, next action. Read this first. |
| `docs/plan/ROADMAP.md` | the phases and releases, and the scope of each |
| `docs/KNOWN-DEFECTS.md` | open and fixed defects |
| `docs/STATUS.md` | **generated** parity board: what passes, what waits on what |
| `docs/superpowers/specs/2026-08-29-fuzzy-regex-port-design.md` | the design, and why |
| `docs/plan/DECISIONS.md` | dated one-liners, append-only |
| `docs/PORTMAP.md` | upstream symbol to C# type - what makes syncs mechanical |

Do not read the whole spec at the start of a session. Read STATE.md and the checklist item's
links; reach for the spec when a decision needs its reasoning.

## Layout

```
src/FuzzyRegex/Parsing/     port of upstream/regex/_regex_core.py
src/FuzzyRegex/Engine/      port of upstream/src/_regex.c
src/FuzzyRegex/Unicode/     tables and the C helpers over them; *.g.cs is generated
src/FuzzyRegex/             public API (port of upstream/regex/_main.py)

tools/build-character-names.py   writes UnicodeCharacterNames.g.cs from the Unicode 18.0.0 UCD
tools/record-unicode-fixtures.py writes the Unicode oracle fixtures for the test suite
tests/FuzzyRegex.Tests/Ported/     translated upstream tests - counts towards parity
tests/FuzzyRegex.Tests/Gaps/       our own tests - does not count towards parity
tests/FuzzyRegex.OracleTests/      differential harness against Python regex
bench/FuzzyRegex.Benchmarks/       BenchmarkDotNet
tools/                      PortTools.psm1, check-ratchet.ps1, run-slices.ps1
upstream/                   read-only submodule, pinned to the commit we track
```

## Commands

```powershell
dotnet tool restore; dotnet husky install     # fresh clone, once: formatting + git hooks
dotnet csharpier format .                     # CI fails on unformatted code
dotnet build                                  # analyzers are errors; there is no warning tier
dotnet test tests/FuzzyRegex.Tests            # the suite
tools/check-ratchet.ps1                       # suite + parity ratchet + regenerate STATUS.md
tools/check-ratchet.ps1 -UpdateBaseline       # only once it is GREEN
tools/run-tool-tests.ps1                      # Pester tests for the tooling above
tools/run-slices.ps1 -DryRun                  # what the autonomous driver would do next
```

`global.json` sets `test.runner` to Microsoft.Testing.Platform, which TUnit needs on the .NET 10
SDK. Without it `dotnet test` fails with a VSTest message.

Everything under `tools/` needs **PowerShell 7** (`pwsh`); the Windows-bundled 5.1 cannot parse
`PortTools.psm1`.

The hooks `dotnet husky install` writes are formatting on `pre-commit` and
`tools/check-ratchet.ps1` on `pre-push`. Tests deliberately do not run on commit: mid-slice
commits are meant to contain failing tests, and the driver has just run the suite anyway.

## House rules

- **Faithful port.** `Parsing/` and `Engine/` mirror upstream's structure, names and control
  flow, so an upstream diff maps onto our files mechanically. Do not tidy, do not restructure,
  do not "improve" a signature. Optimisation is Phase 7 and it is benchmark-driven.
- **Test-first, always.** The test exists and fails before the code exists. Ported tests are
  written skipped in Phase 1 and un-skipped by the slice that delivers their capability.
- **Never weaken a test to get green.** If a ported test looks wrong, prove it by running the
  Python `regex` module and quoting the output, then record the finding in DECISIONS.md.
- **Never edit generated files by hand:** `docs/STATUS.md`, `tests/parity-baseline.json`,
  `src/FuzzyRegex/Unicode/*.g.cs`, `tests/FuzzyRegex.Tests/Gaps/Unicode/*.json`.
- **Never disable an analyzer to get a build.** `.editorconfig` already relaxes, for
  `Parsing/`, `Engine/` and `Unicode/` only, the rules a faithful port must break (method length,
  complexity, nesting, magic numbers, commented-out upstream reference lines). Correctness and
  security rules are errors everywhere and stay that way.
- **UTF-16, not codepoints.** Public indices and lengths are UTF-16 code units, matching .NET
  `Regex`. Upstream indexes by codepoint. Any test whose data contains a non-BMP character needs
  its indices recomputed - verified against Python, never reasoned about.
- **Verification discipline is in `docs/VERIFICATION.md`.** Read it before any review, fix or
  engine slice; it is short and it is the single source. The three rules that catch people out:
  a review finding is a hypothesis until *you* reproduce it (four in five do not survive); one
  review pass per **unreviewed change**, not per slice; and passing the ported suite is evidence
  of parity, not proof of it.
- **Stop rather than guess.** Write the blocker into STATE.md, commit, stop.
- **No `Co-Authored-By` trailer in commit messages.** This repository does not use one.
