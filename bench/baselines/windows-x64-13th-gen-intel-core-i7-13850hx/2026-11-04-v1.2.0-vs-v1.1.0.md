# 1.2.0 against 1.1.0, whole suite (2026-11-03/04)

**Verdict: 1.2.0 runs at 1.1.0's speed within about 1%, and no row is slower beyond noise by more
than 6%.** Across the 91 benchmarks, the median of the 1.2.0/1.1.0 time ratio is 1.014 and the
geometric mean is 1.013. 88 rows move less than their own run-to-run spread. Three rows are slower
beyond it: `MatchesFirstTwo` 1.056, `CountStringMegabyte` 1.036 and `StaticIsMatch` 1.035. The 8 BCL
control rows, which do not run FuzzyRegex, read 0.993-1.002, except `LiteralBclCompiled` at 1.075,
which is inside its own spread. So neither side was disturbed. Each `Matches` call allocates 240
bytes more than in 1.1.0 (D138, deferred to 1.3). `Match` and `IsMatch` allocate the same as before.

## What was measured, and how

- **Trees:** tag `v1.1.0` (`8de8eaf8`) and main at `de4bbc84` (1.2.0's engine; later commits change
  only docs and the version number), each in its own worktree, built in Release before timing.
- **Machine:** `windows-x64-13th-gen-intel-core-i7-13850hx`, Windows 11 23H2 10.0.22631, on mains
  power, with the CPU capped at 4,000 MHz by the Windows power plan (`PROCFREQMAX`), because the
  uncapped laptop crashed under sustained load on 2026-11-02. Absolute times are therefore not
  comparable with earlier notes; ratios are. Nothing else ran: no builds, tests or commits.
- **Runs:** BenchmarkDotNet 0.15.8, .NET SDK 10.0.403, runtime .NET 10.0.14, whole suite,
  `--job medium`, `--affinity 65528` (performance cores, logical processors 3-15). Four passes
  in A-B-B-A order, so that a slow drift falls equally on both sides: 1.1.0 20:23-21:26, 1.2.0
  21:26-22:29, 1.2.0 again 22:29-23:34, 1.1.0 again 23:34-00:38 (UTC+0). A fifth pass on
  `2373e273`, D82's baseline commit, ran 00:38-01:30.
- **Rule:** a row's ratio is the mean of the two 1.2.0 medians over the mean of the two 1.1.0
  medians. Its noise is the larger of the two same-code ratios (1.1.0 second pass over first,
  1.2.0 second over first). A row counts as changed only when its ratio is more than 3% from 1 and
  more than twice its noise. Same-code ratios across the suite: geometric means 0.999 and 1.003,
  single rows 0.93-1.15.
- **Files:** `2026-11-04-v1.1.0-medium.json`, `-medium-b.json` and the two `v1.2.0` files
  (medians, minimums and allocation per pass); `2026-11-04-v1.2.0-vs-v1.1.0-abba.txt` (every row,
  from `.scratch/s1024/bdn-v120-abba.py`); `2026-11-04-v1.2.0-vs-v1.1.0-compare.txt` (the output of
  `tools/compare-benchmarks.ps1` on the first pass of each: GREEN).

The suite as a whole is about 1% slower. That is the size of a fixed cost per call, which fits
the larger engine (the fixes add checks on paths that every match passes). The three rows outside
noise are all short calls, where a fixed cost shows most: `StaticIsMatch` is 286 to 296 ns,
`MatchesFirstTwo` 521 to 551 ns (with the allocation below), and `CountStringMegabyte` counts
matches one call at a time over a megabyte, 957 to 992 µs.

## Allocation

- **Each `Matches` call allocates 240 bytes more** (208 for a fuzzy pattern), once per call and
  not per match: `MatchesFirstTwo` 2,792 to 3,032 B, while `MatchesToEnd` (27 MB) is unchanged.
  Confirmed outside BenchmarkDotNet with `GC.GetAllocatedBytesForCurrentThread` over 1,000 calls
  against both builds: `\w+` 2,816 to 3,056 B, `(\w)+` 4,384 to 4,624 B, `(?:needle){e<=1}` 3,288 to
  3,496 B; `Match` 144 B on both. Source: `MatchState`, which each `Matches` call creates, went
  from 131 to 146 instance fields (about 144 B) and allocates two empty lists eagerly (`CallTracks`,
  `TailTracks`, 32 B each), about 208 B in all; the other 32 B are not yet traced. Registered as
  D138, for release 1.3.
- **Compiling allocates 200-300 bytes more** on the uncached and static-cache rows
  (`UncachedIsMatch` 35,240 to 35,544 B), the D135 cost on patterns without a lookaround. Time on
  those rows: 1.004-1.016, inside noise.
- Every other row allocates the same.

## D82 against its baseline commit

D82 recorded per-call and per-match time rising on main against `2373e273` (2026-09-27). Against
that commit, with 1.2.0's first pass: every row D82 listed is now faster, `StringShort` 0.97,
`SpanShort` 0.90, `StringKilobyte` 0.80, `CountStringMegabyte` 0.65, `BacktrackingPort` 0.93,
`InstanceFuzzyIsMatch` 0.94, `ClassScan` 0.75. Still slower than that commit: compiling, on the
uncached and static-cache rows, 1.26-1.53x the time and 1.14-1.44x the allocation
(`UncachedMatch` 31,408 to 36,256 B), and `CompileLargePattern` allocation 1.09x. Almost all of it
came before 1.1.0. Release 1.3's profiling starts from these rows. One pass only, so read to
about 5%.

## What this means for the 1.2.0 claim

The release notes say 1.2.0 is a correctness release whose matching speed is unchanged. This run
supports that to within about 1% across the suite. The notes now also state the 240 bytes per
`Matches` call.
