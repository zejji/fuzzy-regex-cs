# The 1.0 performance gate (S63, 2026-10-18)

**Verdict: the gate passes.** Of 40 paired workloads, 38 are at or below Python `regex` and 2 are
slower (5%), both within tolerance and neither near 1.25x: ConditionalPerTokenNoMemo 1.09x and
TestedGroupRepeat 1.09x. Two rows are excluded (below). Every `FuzzyPhrase` row is under the 500 ms
per 100,000 records bar; the fastest multi-phrase form is three separate passes (125 ms).

## What was measured, and how

- **Tree:** release candidate, main `5730e15c` (engine as merged at `da587448`), branch `perf/s63-gate`.
- **Machine:** `windows-x64-13th-gen-intel-core-i7-13850hx` (i7-13850HX, 20 cores / 28 logical,
  Windows 11 23H2 10.0.22631), on mains power.
- **Ours:** BenchmarkDotNet 0.15.8, .NET SDK 10.0.402, runtime .NET 10.0.13, Release, the whole suite
  (84 benchmarks), `--job medium` (`IterationCount=15, LaunchCount=2, WarmupCount=10`),
  `--exporters json`, 04:07-05:06 BST. Raw full JSON: `2026-10-18-S63-bdn/`. Summary baseline:
  `net10.0.json` (its `takenUtc` is when the summary was written from the artifacts, not the run).
  No .NET 11 runtime is installed, so only `net10.0` ran.
- **Why medium, not long:** `--job long` is 3 launches of 15 warm-up and 100 measured iterations
  against medium's 2 of 10 and 15, about 6.9 times the iteration work. Medium took 58 minutes on
  2026-10-15, so long would take about six hours, past the five-hour limit the brief set and the
  11:00 commit deadline.
- **Python:** regex 2026.9.10, CPython 3.14.8, pyperf 2.10.0, `bench/baselines/measure_python.py`,
  05:06-05:50 BST straight after the .NET run. Raw JSON: `python-regex.json`. Each row's flags are in
  the table: `V1` throughout, `V0|I` on the `FuzzyPhrase` rows (ledger entry 28).
- **Pinning:** both sides on logical processors 3-15 (mask `FFF8`, performance cores, leaving 0-2
  to the system): `cmd start /affinity FFF8` around each runner, BDN `--affinity 65528`, pyperf
  `--affinity 3-15`. The baselines of 2026-10-13 and 10-15 used all 16 performance-core processors
  (`FFFF`). A check after the run timed the two state classes under both masks: the same numbers
  within 5%, with no direction (`StateByGroupCount(1)` 138.3 ns under FFFF, 138.2 ns under FFF8;
  the widest pair 137.3 and 143.6 ns). The mask did not move the numbers.
- **Quiet machine:** no builds, tests or agents. A 20 s CPU check before each half passed.
  `tools/probes/sample-machine-load.ps1` ran beside both halves (`2026-10-18-S63-load-*.log`): the
  busiest other process in any 30 s window was JetBrains Toolbox, 4.1 s once at 04:45 during the
  .NET run and 4.1 s once at 05:47 during the Python run; everything else stayed under 1 s.
- **Noise floor:** 1.10 for time, 1.0001 or 1,024 B for allocation (`noise-floor.md`, pinned A/B of
  2026-10-13).

**Excluded:**

- EnumerateMatchesSpanToEndDense: a Span overload; Python has no counterpart. Its `str` walk, EnumerateMatchesToEndDense, is in the gate (0.42x).
- EmptyIterationRecord: upstream is exponential on `^(?:(?=(a))|a)*\1?$` and gives neither a time nor an answer over the row's 200 a's (measured 2026-10-11); the port answers in 3.6 ms (D17).

**FuzzyPhrase, against 500 ms per 100,000 records:** OneIsMatch 44.0 ms, OneMatch 45.2 ms, OneEnhanced 48.4 ms; ThreeSeparatePasses 125 ms, ThreeNamedList 136 ms, ThreeAlternation 139 ms. All under the bar. Fastest multi-phrase form: three separate passes, about 10% faster than one alternation (125 against 139 ms).

## The two slower rows (decision 3: accepted for 1.0, listed in the release notes)

Performance work is frozen for 1.0 (plan `2026-10-16-plan-to-1.0.md`, decision 3), so neither row
gets a fix now. Both are within the gate's tolerance; they are listed so the release notes can name
them, and each has a 1.1 route.

- **ConditionalPerTokenNoMemo, 1.09x** (114 ms against 105 ms; 0.99x on 2026-10-15). It now
  allocates 105,408,000 bytes an operation where the 10-15 baseline allocated none, and its time
  rose 1.10x. Something merged between `432ced01` and `5730e15c` (the D85-D102 correctness work)
  allocates on this path; not yet bisected. 1.1 route: bisect the merges, then the allocation fix
  (`OPTIMISATION-TECHNIQUES.md`, allocation elimination first); the memo's backreference key (BR)
  remains the algorithmic fix for the time.
- **TestedGroupRepeat, 1.09x** (2.44 ms against 2.24 ms; 1.05x on 10-15). Same cause as before: the
  backreference turns the failure memo off for the whole pattern. It now also allocates 7 bytes an
  operation (amortised; 0 on 10-15). 1.1 route: the BR memo key (plan section 5, item 6).

## Against the 2026-10-15 baseline (not the gate)

`2026-10-18-S63-compare-vs-2026-10-15.txt`, at the 1.10 floor. Tree `432ced01` against `5730e15c`,
138 commits apart. No row crossed the floor in the faster direction. Slower beyond the floor:

- EmptyIterationRecord 1.31x (excluded from the gate), BacktrackingPort 1.22x, MatchesFirstTwo
  1.21x, the match-state rows (StateByGroupCount 1.11-1.18x, StateBySubjectLength 1.13-1.14x),
  the SpanOverload rows 1.12-1.13x, ConditionalPerToken 1.13x, SplitLong 1.11x,
  PathologicalSameBranches 1.11x, InstanceFuzzyIsMatch 1.11x, ConditionalPerTokenNoMemo 1.10x.
- New allocation: ConditionalPerTokenNoMemo (0 to 105,408,000 B), CaseBlindAlternation (0 to 52 B),
  TestedGroupRepeat (0 to 7 B).

The core-mask check above rules out pinning as the cause of the state rows, so the per-match fixed
cost (constructing match state) has grown by roughly 10-15% since 10-15. It is small in absolute
terms (tens of nanoseconds) and touches every row, which is why the nanosecond-scale rows show it
most. None of it changes the gate verdict. For 1.1: bisect the D85-D102 merges for the state-cost
rise and the new allocations.
