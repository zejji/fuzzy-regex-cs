# 1.1.0 against 1.0.0, the whole suite (2026-10-31)

**Verdict: 1.1.0 is faster on most of the suite and slower on none beyond noise.** Across the 76
FuzzyRegex benchmarks the median time is 0.92 of 1.0.0's (geometric mean 0.91). 49 rows are at
least 5% faster, the best `CaseBlindAlternation` at 0.26x; no row is more than 3.3% slower, which is
inside the run-to-run spread, so none was re-timed. The 8 BCL control rows, which do not run
FuzzyRegex, read 0.99-1.01, so neither pass was disturbed.

## What was measured, and how

- **Trees:** tag `v1.0.0` (`3810e6a9`) and tag `v1.1.0` (`8de8eaf8`), each in its own worktree,
  built in Release before timing.
- **Machine:** `windows-x64-13th-gen-intel-core-i7-13850hx`, Windows 11 23H2 10.0.22631, on mains
  power. Nothing else ran: builders paused, no builds, tests or commits.
- **Runs:** BenchmarkDotNet 0.15.8, .NET SDK 10.0.403, runtime .NET 10.0.14, the whole suite,
  `--job medium`, `--affinity 65528` (performance cores, logical processors 3-15). Two passes back
  to back: 1.0.0 01:52-02:51, then 1.1.0 02:51-03:56 (UTC+0). The CPU temperature reader was offline,
  so temperatures were not logged.
- **Drift check instead of a third pass:** the BCL rows in `ReferenceBenchmarks` read 0.989-1.013.
- **Files:** `2026-10-31-v1.0.0-medium.json` and `2026-10-31-v1.1.0-medium.json` (medians, minimums,
  allocation), and `2026-10-31-v1.1.0-vs-v1.0.0-compare.txt` (the output of
  `tools/compare-benchmarks.ps1`). Six benchmarks added after 1.0.0 have no 1.0.0 row.

## Allocation

Unchanged on every row except a few bytes more per compile: 8 B on the four uncached or
static-cache compile rows (`UncachedIsMatch` 35,232 to 35,240 B), 56 B on `CompileLargePattern`
(1,016,616 to 1,016,672 B), and 158 B and 21 B on `MatchesToEnd` and `SplitLong`, whose
allocations are 27 MB and 1.7 MB. All are below the comparison's floor of 1,024 B.

## What this means for the 1.1.0 claim

The CHANGELOG and the GitHub release say matching is faster on most of the benchmark suite, and
that 1.1.0 had not been timed against 1.0.0 as a whole. This run does that and supports the claim.
The "9-25% off most benchmarks" figure measured against the code before each change is borne out
in range: the middle of the suite is about 8% faster, a third of it 10% or more.
