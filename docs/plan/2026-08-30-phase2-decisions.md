# Phase 2 decisions A-D: background, options and recommendations

Written 2026-08-30 to support the owner's Phase 2 checkpoint, and kept as the record of why the
Phase 2 slices are shaped as they are. Every measurement below was taken on this machine on that
date unless a source is cited.

**Outcome (decided by the owner, 2026-08-30):** all four recommendations accepted.

| Decision | Chosen | Where it lands |
|---|---|---|
| A. Unicode tables | A2: transliterate `_regex_unicode.c`; generator project deleted | S09; spec amendment 11 |
| B. `\N{name}` | B2: name table generated from UCD 17.0.0 | S09 |
| C. `ExplicitCapture`, `Unescape` | C2: remove both | S07 removes `ExplicitCapture`, S12 removes `Unescape` |
| D. Deferred `Match` and option members | Add nothing in Phase 2 | S12 records it |

## 1. What Phase 2 is, in one paragraph

Upstream `regex` has two halves. The Python half (`_regex_core.py`, 4,676 lines) reads a pattern
such as `(?i)ab+c|\d{2,}` and turns it into a flat list of integers called bytecode. The C half
(`_regex.c`, 26,655 lines) is the matching engine that executes that bytecode against a subject
string. Phase 2 ports the Python half. Phase 3 onwards ports the C half. At the end of Phase 2 we
can compile any pattern upstream can, and prove the integers are identical to upstream's for the
1,534 patterns its own test suite compiles, but we still cannot match anything.

Two properties of a "faithful port" matter for every decision below:

- **Structure follows upstream** so that a future upstream change maps onto one of our files
  mechanically. Anything we add that upstream does not have is something no upstream test, no
  upstream bug fix and no oracle will ever check for us.
- **The shipped package carries zero runtime dependencies** (DECISIONS 2026-08-29). Anything we
  need at runtime, we must ship ourselves.

## 2. Background for A and B: the parser needs Unicode data

It is easy to assume Unicode is an engine concern. It is not only that. The parser consults
Unicode data in three ways, and every one of them changes the bytecode it emits:

1. **Property names.** `\p{Greek}` is compiled to the opcode `PROPERTY` followed by a number
   that identifies the property and value (`0x5570 05` for `Script=Greek`). The number comes from
   a table of 185 property names and 1,704 value names (`_regex_unicode.h`). Without the table
   the parser cannot even reject a misspelt property name.
2. **Case folding.** Under `(?i)`, `Range.optimise` asks "which characters fold to something in
   this range?" and `Branch._reduce_to_set` asks "do these two characters have the same folded
   form?" (`_regex_core.py:364-368`, `:3394-3425`). The answers alter which opcodes are emitted.
3. **Character names.** `\N{LATIN SMALL LETTER A}` needs a name-to-codepoint dictionary
   (`_regex_core.py:1444`).

Upstream gets 1 and 2 from C functions over a generated 31,586-line C file, and 3 from Python's
standard library. That split is why A and B are two separate decisions: upstream ships the data
for 1 and 2 but not for 3.

The roadmap had placed "Unicode generator" in Phase 6, after the whole engine. The measurement
above shows that is a plan defect: most of the compile-parity corpus (1,534 patterns; 32 distinct
flag combinations, most involving `(?i)`) cannot be verified without 1 and 2. Both must land in
Phase 2, before slice S10.

## 3. Decision A: how to get the Unicode tables into C#

### What the data looks like

`upstream/src/_regex_unicode.c` is entirely machine-generated by `tools/build_regex_unicode.py`
(1,785 lines of Python) from the Unicode Character Database (UCD), the set of text files the
Unicode Consortium publishes with each version. Measured composition of the C file:

- about 250 plain data arrays of 8- and 16-bit unsigned integers;
- three arrays of small structs (case variants, full case foldings, script extensions);
- three string and index tables (property names, value names, the strings they point at);
- 104 lookup functions, all built from roughly twenty statement shapes.

A typical lookup function is a three-level table walk. Given a codepoint, it splits the number
into three bit fields and uses each to index the next table:

```c
RE_UINT32 re_get_general_category(RE_UINT32 codepoint) {
    field_2 = codepoint >> 10;
    field_1 = (codepoint >> 5) & 0x1F;
    field_0 = codepoint & 0x1F;
    v = re_general_category_table_1[field_2];
    v = re_general_category_table_2[(v << 5) | field_1];
    v = re_general_category_table_3[(v << 5) | field_0];
    return v;
}
```

Every one of the 104 functions is a small variation on this. There is no hand-written logic in
the file.

### The options

**Option A1: port the Python generator to a C# console tool** (what the design spec, section 6,
currently says). We would write `src/FuzzyRegex.UnicodeGenerator/`, a C# program that downloads
or reads `UCD.zip`, parses the same dozen UCD text files the Python script parses, runs the same
range-merging and table-compression logic, and emits `Unicode/*.cs`.

- For: independent of upstream's generated output; can regenerate for a Unicode version upstream
  has not shipped yet; matches what the spec says.
- Against: a second 1,800-line program with its own bugs. Its output can only be verified by
  comparing with upstream's tables anyway, so the comparison must be built regardless. Needs the
  UCD download (network, a few megabytes) as a build-time input. The one thing it can do that
  A2 cannot, regenerating ahead of upstream, is something a port pinned to an upstream commit
  never does: our tables must match upstream's tables at the pin, or the oracle reports every
  difference as a defect.

**Option A2: transliterate upstream's generated C file into C#** (recommended). A script reads
`_regex_unicode.c` and `_regex_unicode.h` and writes `Unicode/*.cs`: each array becomes a
`static ReadOnlySpan<byte>` or `ReadOnlySpan<ushort>` over an array literal (which the C#
compiler stores as read-only static data with no allocation, the pattern spec section 4 already
names), each function becomes the same three lines of C#, each `#define` a constant.

- For: table parity with upstream **by construction**, because the numbers are copied, not
  recomputed. No UCD download. An upstream Unicode bump becomes "bump the submodule, re-run the
  script", which is strictly less work than A1's "download UCD, regenerate, compare", because
  upstream has already done the generating and checked the result in. The script is small
  (twenty statement shapes) and can assert it consumed every table and function, so a new shape
  in a future upstream file fails loudly rather than dropping data silently.
- Against: departs from the spec's wording. We depend on upstream's generator being right, but
  we depend on that anyway: the oracle we compare against is upstream, tables included. It does
  not give us a way to fix a Unicode data bug independently of upstream; nor does the spec's
  approach in practice, since a divergence from upstream fails the oracle.

**Option A3: both.** Port the generator and also verify it against a transliteration.

- For: maximum independence.
- Against: double the work for the same tables. The spec's own risk table says table correctness
  is proven "by oracle tests, not by reviewing generated output"; A3 adds a second thing to
  review instead.

### An illustrative example of the risk A1 carries

`build_regex_unicode.py` decides table depth and field widths by trying compressions and keeping
the smallest (`generate_lookup`, lines 846-946). A port that got one tie-break differently would
produce tables that are semantically identical but numerically different, and every
`PROPERTY`-carrying bytecode row in the compile-parity corpus would then differ from upstream's,
even though matching would be correct. We would spend a slice chasing a non-bug. A2 cannot have
this failure.

### Recommendation

A2. Delete `src/FuzzyRegex.UnicodeGenerator/` (its `Program.cs` is a two-line stub that prints
"not implemented"), amend spec section 6 to say the tables are transliterated from upstream's
generated source, and note that the UCD is still needed for one thing, which is decision B.

## 4. Decision B: `\N{name}` character names

### What the construct is

`\N{LATIN SMALL LETTER A}` in a pattern means the character whose Unicode name is given.
Upstream implements it in five lines:

```python
value = unicodedata.lookup(name)      # _regex_core.py:1444
return make_character(info, ord(value), in_set)
```

`unicodedata` is CPython's standard-library Unicode database. `lookup` accepts the formal name
of any assigned character, the formal aliases in `NameAliases.txt` (for example
`LATIN CAPITAL LETTER GHA`, an alias for `LATIN CAPITAL LETTER OI`, U+01A2), and named sequences.
Measured: upstream accepts the alias in a pattern; a named sequence (two codepoints) makes
`ord()` fail with a `TypeError`, so in practice only single-character names work.

.NET has no equivalent. `System.Globalization.CharUnicodeInfo` exposes categories, numeric values
and a few properties but not names; there is no built-in API for a character's name in .NET as of
2026 ([Meziantou](https://www.meziantou.net/get-a-unicode-character-name-from-a-rune-in-dotnet.htm),
[.NET Ramblings](https://www.dotnetramblings.com/post/27_07_2026/27_07_2026_11/)). The community
answers are a NuGet package or calling the operating system's ICU library, and both are ruled out
below.

### How much it matters

Upstream's test suite uses `\N{...}` 97 times. Our ported tests carry 41 of them across nine
files (`CaseFoldingTests`, `FuzzyExtendedSyntaxTests`, the `Regressions` files and others). One of
S05's two non-BMP data sites is a `\N{SMILING CAT FACE WITH OPEN MOUTH}`. Without a name table,
41 ported tests can never pass and the port is visibly less than upstream in an area its own
users use.

### The size question, measured

There are 148,853 named codepoints in Unicode 16.0.0 (the version the local CPython 3.14
carries). Most names are algorithmic and need no storage: `CJK UNIFIED IDEOGRAPH-4E00`,
`HANGUL SYLLABLE GA` (computed from the syllable's jamo), `TANGUT IDEOGRAPH-17000` and similar
ranges cover 114,716 of them. The remaining **34,137 names total 1,065 KB of text, zlib-compress
to 211 KB, and use only 13,532 distinct words at 3.9 words per name**, so a word-tokenised table
(the technique Perl and ICU use) lands around 200-300 KB in the shipped assembly. For scale, the
Unicode tables from decision A are of the same order, and `System.Text.RegularExpressions`'s own
casing and category tables are a few hundred kilobytes too. Unicode 17.0.0 adds 4,803 characters
([Unicode blog, 9 Sep 2025](https://blog.unicode.org/2025/09/unicode-170-release-announcement.html)),
4,298 of them CJK ideographs with algorithmic names, so the stored table grows by only a few
hundred names.

### The options

**Option B1: do not support `\N{}`.** The parser raises upstream's own error, "undefined
character name", for every name.

- For: zero work, zero bytes.
- Against: 41 ported tests permanently red-by-design, a documented parity hole in a user-visible
  feature, and a second class of pattern that compiles upstream and not here. It is the wrong
  place to cut a corner for a project whose stated v1.0 definition is "all applicable upstream
  tests ported and passing".

**Option B2: generate a name table from the UCD at Unicode 17.0.0** (recommended). A script in
`tools/` reads `UnicodeData.txt` and `NameAliases.txt` from the 17.0.0 UCD, emits a compact
table into `Unicode/`, and a small lookup implements `unicodedata.lookup`'s contract (formal
names and aliases, case-insensitive, single characters only, which is all upstream can use).

- For: complete parity with upstream's *intent*. Upstream's tables are 17.0.0; a pattern that
  says `\N{SAUDI RIYAL SIGN}` (new in 17.0.0) names a character `\p{Sc}` already matches here.
  Deterministic, committed, no runtime dependency, roughly a quarter megabyte.
- Against: the only place a UCD download is still needed. Diverges from the *local* oracle:
  CPython 3.14's `unicodedata` is 16.0.0 ([Python docs](https://docs.python.org/3/library/unicodedata.html)),
  so the 500-odd non-algorithmic names new in 17.0.0 resolve here and raise there. That is a
  known, recordable divergence, and CPython 3.15 moves to 17.0.0, at which point it disappears.

**Option B3: generate the table at Unicode 16.0.0 to match the local oracle exactly.**

- For: the local Python oracle and the port agree on every name today.
- Against: it copies an accident. Upstream's author did not choose 16.0.0; the host Python did.
  The disagreement comes back the other way the moment the oracle runs on Python 3.15, and the
  CI oracle (built from upstream on `ubuntu-latest`'s Python) will change under us anyway. We
  would be pinning our behaviour to whatever CPython the developer happens to have.

**Option B4: a third-party NuGet package such as `UnicodeInformation`.**

- Against: breaks the zero-runtime-dependency rule, pins us to someone else's Unicode version
  and release cadence, and pulls in far more data than names.

**Option B5: call the operating system's ICU library.**

- Against: behaviour differs by OS and OS version; `InvariantGlobalization` is on in this repo,
  which turns ICU off; and it cannot be tested deterministically across the three CI operating
  systems.

### Recommendation

B2, with the divergence from CPython 3.14's `unicodedata` recorded in DECISIONS and a test that
checks every 16.0.0 name against the local Python (as a single hash) and the 17.0.0 additions by
count against the UCD's `DerivedAge.txt`.

## 5. Decision C: `ExplicitCapture` and `Unescape`

Both were added in S01, when the public surface was written as signatures only, by analogy with
`System.Text.RegularExpressions.Regex`. Neither has an upstream counterpart. Neither is used by
any ported test (measured: zero references outside the S01 stub tests).

### What they are

`RegexOptions.ExplicitCapture` in .NET makes plain `(...)` groups non-capturing, so only named
groups capture. Upstream has no such flag; a user who wants a non-capturing group writes
`(?:...)`. Implementing it means adding a branch in `parse_paren` that upstream does not have.

`Regex.Unescape` reverses `Regex.Escape`: it turns `\.` back into `.` and also decodes `\n`,
`\x41` and similar. Upstream has `escape` (`_main.py:388`) and nothing in the other direction.

### The options

**Option C1: implement both.**

- For: a .NET user might expect them.
- Against: the compile-parity corpus can only verify constructs upstream has, so both would be
  the only unverified logic in the parser. `ExplicitCapture` in particular changes group
  numbering, and group numbering is the most error-prone bookkeeping in the parser (S11 notes).
  `Unescape` has no defined semantics against upstream's escape rules, so we would be inventing
  behaviour: for example, does it decode `\N{...}`? Upstream's own `escape` never emits one.

**Option C2: remove both now** (recommended). Public API can change freely before 1.0 (spec
section 1 says the working name itself is still cheap to change).

- For: nothing unverifiable in the parser; less public surface to document and keep.
- Against: a .NET user who wants "only named groups capture" writes `(?:...)` on unnamed groups
  as upstream users do. A user who wants to undo `Escape` keeps the original string.

**Option C3: keep the signatures, throw `NotSupportedException`, decide at 1.0.**

- Against: a public member that always throws is worse than one that does not exist; it shows up
  in IntelliSense and in the API docs.

### Recommendation

C2. If real demand appears after 1.0, `ExplicitCapture` can be added as a documented deviation
with its own tests; nothing about removing it now forecloses that.

## 6. Decision D: the deferred API questions

Four small questions Phase 1 postponed. Each is "should our `Match` or `FuzzyRegex` type carry a
member upstream has", and each has the same shape: the information is already reachable another
way, so the question is convenience versus surface area. Evidence is counted from
`upstream/regex/tests/test_regex.py`.

### D1. `Match.pos`, `Match.endpos`, `Match.string`, `Match.re`

Read-back properties: the search bounds, the subject, and the pattern object a match came from.

- Upstream usage: 4 reads in the whole suite, all in `test_getattr` (lines 473-477).
- .NET precedent: `System.Text.RegularExpressions.Match` exposes none of them; the subject is an
  internal field.
- The bounds are already what the caller passed as `beginning` and `length`.

Recommendation: do not add. Record the count in PORTMAP, which already says "Phase 2 decides".

### D2. `Match.allcaptures`, `Match.allspans`, `Match.groupdict`, `Match.capturesdict`

Convenience shapes over data `Groups` and `Group.Captures` already hold: every group's capture
list as a tuple of tuples; every group's spans; a dictionary keyed by group name.

- Upstream usage: 15 lines across the suite. S05 ported all of them through `Groups`, `Captures`
  and LINQ, with a comment at each site.
- .NET precedent: `GroupCollection` is already indexable by name, which is what `groupdict` gives
  a Python caller.

Recommendation: do not add for Phase 2. These are cheap to add in Phase 3 when `Match` becomes
real, if their absence makes the ported tests noticeably worse to read; nothing is lost by
waiting until there is a working `Match` to design them against.

### D3. `WORD` and `ASCII` as public options

Upstream flags `regex.WORD` (`(?w)`, Unicode default word boundaries) and `regex.ASCII` (`(?a)`,
ASCII-only `\w`, `\d`, `\b`). `FuzzyRegexOptions` does not expose them; DECISIONS 2026-08-30
records that every ported test using them was rewritten to the inline form, which the oracle
proved equivalent (28 assertions).

- Upstream usage: 73 occurrences of `(?w` or `(?a` in the suite; the parser must support the
  inline forms regardless (S10).
- Adding public members costs nothing in the parser (the bit already exists internally) but adds
  two option-handling paths that the corpus cannot distinguish from the inline form.

Recommendation: leave internal for Phase 2. Add `Word` and `Ascii` to the public enum in Phase 3
if a .NET-style caller needs them, at which point the match oracle can verify them.

### D4. Summary of D

All four: do not add now. None blocks a ported test, all are additive later, and Phase 3 is the
first point at which a `Match` exists to design against.

## 7. Everything on one page

| Decision | Recommendation | What it costs | What it buys |
|---|---|---|---|
| A. Unicode tables | Transliterate `_regex_unicode.c`; delete the generator project; amend spec section 6 | A ~300-line script; a spec amendment | Table parity by construction; no UCD download; cheaper upstream syncs |
| B. `\N{name}` | Generate a name table from UCD 17.0.0; record divergence from CPython 3.14 | One UCD download at generation time; ~250 KB in the assembly | 41 ported tests can pass; parity with upstream's intended Unicode version |
| C. `ExplicitCapture`, `Unescape` | Remove | Two members nobody uses | No unverifiable logic in the parser |
| D. Deferred `Match` and option members | Do not add in Phase 2 | Nothing now | Decide against a real `Match` in Phase 3 |

If any recommendation is rejected, the slice files already say what changes: S09 splits into two
if A1 is chosen; S07 gains the `ExplicitCapture` branch and S12 gains `Unescape` if C1 is chosen;
S12 records D whichever way it goes.
