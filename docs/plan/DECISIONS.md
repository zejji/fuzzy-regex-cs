# Decisions

Append-only. One dated line per decision a future session would otherwise have to re-derive.
Never edit or delete an entry: if a decision is reversed, add a new line saying so.

- 2026-08-29 Port target is mrab-regex at `1760a20647f1c2ddcc025128407fe6f7edb905a1` (release 2026.8.12), pinned as the `upstream/` submodule.
- 2026-08-29 SDK pinned to 10.0.400 with `rollForward: latestPatch` in `global.json`; `test.runner` set to Microsoft.Testing.Platform, which TUnit requires on the .NET 10 SDK.
- 2026-08-29 Analyzer set copied from an earlier internal monorepo (Meziantou, SonarAnalyzer, SharpSource, ErrorProne.NET) with warnings as errors, but **not** its `CommunityToolkit.Diagnostics` reference: the shipped package must carry zero runtime dependencies.
- 2026-08-29 Analyzer rules that a faithful port must violate (method length, complexity, nesting, magic numbers, commented-out upstream code, `NotImplementedException`) are relaxed in `.editorconfig` for `src/FuzzyRegex/Parsing` and `Engine` **only**. Correctness and security rules stay as errors everywhere. Rationale: upstream's structure must be preserved for syncs to stay mechanical, and autonomous slice sessions should spend allowance porting, not restructuring to satisfy a style rule.
- 2026-08-29 Test identity for the parity ratchet is `className + "." + testName` from the TRX report; the baseline stores the sorted **set** of passing ids rather than a count, so a slice's diff shows exactly which tests it enabled and a swap cannot hide behind an unchanged total.
- 2026-08-29 Feature area for `docs/STATUS.md` is derived from the test namespace (`Fuzzy.Text.RegularExpressions.Tests.Ported.<Area>`), and the capability a skipped test waits on is parsed from its `[Skip("needs:...")]` reason. Both conventions are enforced by a test (`PortedTestConventionsTests`), because a silent mis-parse would report fake progress.
- 2026-08-29 Budget gate: validated that **no local source reports live plan utilisation**. `~/.claude/stats-cache.json` lags by weeks and has no plan denominator; a `rateLimit` record appears only after a request has already been rejected (429); the claude.ai usage page needs an interactive browser, which an unattended `claude -p` driver has not got. The gate is therefore the deterministic slice caps (spec section 9's sanctioned fallback), plus rolling 24h/7d token windows computed from `~/.claude/projects/**/*.jsonl`, plus a back-off while a recorded rate-limit reset is still in the future.
- 2026-08-29 Budget token metric is the plain sum of all four token types, cache reads included, counted **globally** across every Claude Code session on the machine. Measured that day: about 2.9e9 tokens/day and 1.98e10/week.
- 2026-08-29 Token caps are a **circuit breaker, not a rationing mechanism**; the slice caps do the rationing. Setting the token caps at half of typical usage was tried and rejected: a dry run of the driver refused the very first slice, because an ordinary working day passes that mark by the afternoon. They now sit at roughly 2x the measured daily figure so they only trip on a runaway.
- 2026-08-29 `check-ratchet.ps1 -AcceptRemovals` is the only sanctioned way to retire a baselined test. A rename and a lost test look identical from outside, so removals go red by default; accepting them lists each one. Hand-editing `tests/parity-baseline.json` is forbidden because it would let real coverage loss through unnoticed.
- 2026-08-29 Skip reasons name a **capability** (`needs:lookbehind`), not a slice id, and Phase 1 opens with an API surface stub (slice S01). Both resolve contradictions in the design spec as originally written; the spec is amended inline and the changes are listed in its section 15.
- 2026-08-29 Per-slice cost is measured from `claude -p --output-format json`, which returns `usage`, `total_cost_usd`, `is_error` and `permission_denials` - more reliable than scraping session logs.
- 2026-08-29 The driver passes a scoped tool allowlist (Read/Write/Edit/Glob/Grep/TodoWrite/Skill/Task/Agent and Bash limited to dotnet, git, pwsh and python) with `--permission-mode acceptEdits`. No blanket permission bypass: an unattended session must not be able to run arbitrary commands on the machine.
- 2026-08-29 Python oracle runs `regex` **2026.7.19** from PyPI locally; the pinned submodule commit is tagged 2026.8.12, which upstream never published. **The gap is immaterial and this is measured, not assumed**: `git diff 0525aff..1760a20` (the 2026.7.19 tag to the pin) touches only `pyproject.toml`, `changelog.txt`, `.github/workflows/main.yml` and the `__version__` string in `regex/_main.py`. `src/_regex.c`, `src/_regex_unicode.c`, `regex/_regex_core.py` and `regex/tests/test_regex.py` are byte-identical, so matching behaviour is the same. Re-run that diff before trusting this at the next sync.
- 2026-08-29 The oracle in CI is **built from `upstream/`**, not installed from PyPI, so the ground truth is exactly the pinned commit; the Linux runners already have a compiler, so it costs nothing. `oracle.yml` asserts the built version equals the version in `upstream/pyproject.toml` - a silently mismatched oracle would report version drift as port defects. Verified the assertion has teeth by running it against the local 2026.7.19: it fails.
- 2026-08-29 **No C compiler installed on the Windows dev box**, deliberately. There is no MSVC at all, so a local from-source build means 3-7 GB of VS Build Tools, and for the current pin it would buy nothing but a different version string. Install it at the first upstream sync where the pinned commit genuinely differs from a published release - `sync-upstream` says how and when.
- 2026-08-29 Pester 6.1.0 installed for the PowerShell tooling tests (only the Windows-bundled Pester 3.4.0 was present, whose syntax is incompatible).
- 2026-08-29 `docs/STATUS.md` carries no timestamp and is written with LF endings, and `.gitattributes` sets `eol=lf` repo-wide. CI regenerates the board and fails on any diff; a wall-clock stamp made that check fail on every run, and a CRLF/LF flip rewrote every line on the Linux and macOS legs.
- 2026-08-29 `docs/plan/slice-log.jsonl` is gitignored. The budget gate counts slices from it, and the failed-slice rollback runs `git clean -fd`, which would have deleted it and reset the driver's daily cap to zero. Verified that `git clean -fd` (no `-x`) leaves ignored files alone.
- 2026-08-29 The driver launches `claude` through `ProcessStartInfo.ArgumentList`, not `Start-Process -ArgumentList`. The latter joins arguments with spaces and quotes nothing, so `Bash(dotnet *)` reached the CLI as two tokens and the scoped allowlist - the whole safety boundary for an unattended session - silently did not apply.
- 2026-08-29 A failed slice rolls back to the head recorded before the session, not to `HEAD`. A session can commit its work and move its slice file to `done/` and still leave the ratchet red; resetting to `HEAD` kept that commit and stranded the slice where it would never be retried.
- 2026-08-29 The editorconfig section for the port relaxations is `[src/FuzzyRegex/{Parsing,Engine}/**.cs]`. The obvious `**/*.cs` form requires an intervening directory, so it matched nothing directly inside `Parsing/` or `Engine/` - exactly where the ported engine lives - and every relaxation was inert. Verified with a probe file before and after.
- 2026-08-29 Phase 0 closed with a blind review that found eight defects, all confirmed and fixed. Five were in the slice driver and the ratchet, none would have been caught by the tests as they stood, and each fix that had testable logic gained a test. Worth repeating per slice as the spec requires.
- 2026-08-29 The root namespace is `Fuzzy.Text.RegularExpressions`, not `FuzzyRegex` (design spec amendment 8). A type cannot be named after its containing namespace and stay reachable: with namespace `FuzzyRegex` and entry type `FuzzyRegex`, a consumer writing `using FuzzyRegex;` gets `CS0118: 'FuzzyRegex' is a namespace but is used like a type` on `new FuzzyRegex(...)` and CS0234 on `FuzzyRegex.IsMatch(...)`. Measured with a throwaway project against the built library, not reasoned about; MA0049 flagged it and the suppression was rejected in favour of the fix. Assembly, NuGet id and every directory keep the name `FuzzyRegex`; test and benchmark namespaces moved too, because `FuzzyRegex.Tests.*` declared the colliding namespace itself.
- 2026-08-29 `FuzzyRegex.Match` keeps the .NET meaning (search anywhere, upstream's `search`); upstream's anchored `match` is `MatchAtStart` and `fullmatch` is `FullMatch`. Naming upstream's `match` `Match` would have silently given a .NET caller anchored behaviour - a trap no compiler catches. Static conveniences take `(input, pattern, options)`, `Regex`'s argument order rather than upstream's.
- 2026-08-29 S01's surface is wider than its slice file listed, by owner approval: the listed members could not express `fullmatch` (71 uses in the upstream suite), `partial` (91), `overlapped` (15), `pos`/`endpos` (22/14), `subn` (17) or `expand` (8), and S01's whole purpose is to be a compilation target for S02-S05. Counting the real usage first turned "is the stub wide enough?" from an opinion into a number.
- 2026-08-29 `FuzzyRegexOptions` uses upstream's `RegexFlag` bit values (`_regex_core.py:73-90`) rather than `RegexOptions`'s, so the parser port compares against upstream's tables directly. Nothing casts between the two enums, so the numbers need not agree with the built-in engine's.
- 2026-08-29 The pre-commit hook (slice S01b) formats and does not run tests; the suite belongs on pre-push and in CI. `run-slices.ps1` commits at the end of every slice moments after `check-ratchet.ps1` has run the whole suite, so a test-running pre-commit hook would run it twice per slice for no new information - and mid-slice TDD commits are *meant* to have failing tests. A local hook is also one `--no-verify` away from irrelevant, so it cannot be the gate; CI and the ratchet are.
- 2026-08-29 .gitignore negates `*.trx` for tools/tests/fixtures/. The Pester fixture sample.trx is an input that PortTools.Tests.ps1 reads, not test output, and the blanket `*.trx` rule meant it had never been committed - so the CI "Tooling tests (Pester)" step had been running against a file that does not exist on a fresh clone since Phase 0. `TestResults/` already covers the real test output on its own line. Found while committing S01, whose fix to that fixture was otherwise uncommittable.
- 2026-08-29 Review discipline is an evidence gate, not a pass count (spec amendment 9). The old wording, "one pass, no loops", conflated a critique loop (reviewer opines, code changes, reviewer opines again - genuinely harmful, stays banned) with repair against execution feedback (a red ratchet or an oracle divergence - ground truth, and two rounds capture 76-95% of achievable improvement across seven models with no model regressing, arXiv:2604.10508). It also read as one pass per *slice* rather than per *unreviewed change*, which is how S01 shipped ~200 lines of public API no reviewer had seen. Reviewers now hand over a reproduction rather than prose, and are not asked for explanations or proposed corrections, which measurably raise misjudgement (arXiv:2603.00539).
- 2026-08-29 Every review finding is reproduced before it is acted on. An adversarial gate of this shape killed ~79% of 171 candidate findings before advancement (arXiv:2604.19049), and removing execution-grounded validation from an agentic repair pipeline increased unnecessary repairs by 131.7% (arXiv:2604.10800). Automated code review is imprecise enough to need this: four techniques benchmarked in arXiv:2509.01494 scored between 2.79% and 9.22% precision. In S01 both reviews were reproduced finding by finding before any code changed.
- 2026-08-29 The differential oracle moves from Phase 6 to the start of Phase 3 (spec amendment 10). Scheduling the third correctness leg after the entire engine left Phases 3-5 resting on the ported suite and the ratchet alone, and those cannot carry it: in the closest published analogue only 72% of LLM-transpiled functions were semantically equivalent despite compiling and passing the existing tests (56.3-92.1% by codebase), with differential testing against the reference catching the rest at 85.7-88.2% precision and 100% recall (arXiv:2510.07604). Infrastructure already exists from Phase 0, so this changes when the harness is written, not what has to be built. The dialect-divergence caveat that normally weakens cross-engine differential testing (arXiv:2603.00311) does not apply: we compare against the exact upstream commit we are a port of, not across dialects.
- 2026-08-29 There is no `.csharpierrc`; `.editorconfig` is the only formatting configuration. CSharpier 1.3.0 reads `indent_style`, `indent_size` and `max_line_length` from `.editorconfig` directly, so a second config file would only be a place for the two to drift apart - the exact failure S01b exists to prevent. Measured, not assumed: a 112-character line wraps under CSharpier's default `printWidth` of 100 and survives untouched once `max_line_length = 120` is present. `endOfLine` is left at `auto`, which preserves what is there, and `.gitattributes` already pins that to LF repo-wide.
- 2026-08-29 CSharpier formats `src/FuzzyRegex/Parsing` and `Engine` like everything else - no ignore entry. The concern was that reflowing a hand-port would break the by-eye mapping onto `_regex_core.py` and `_regex.c`. Probed against the shapes those ports will actually take (dispatch dictionaries, opcode-name tables, a `case`-per-opcode switch, an if/elif chain, quoted upstream reference comments): CSharpier never reorders a statement, never touches a comment, and left the switch alone. It only rewraps, and for a table that means one entry per line, which makes an upstream entry appearing or disappearing a one-line diff rather than a three-row reflow. Where a specific grid must survive verbatim, `// csharpier-ignore` above it holds - verified on an aligned numeric table.
- 2026-08-29 There is no `.csharpierignore`. CSharpier already skips `obj`, `node_modules`, `.git` and `*.g.cs` by default and honours `.gitignore`, which covers `bin/` and `TestResults/`; `upstream/` contains no C# at all. `csharpier check .` reports 20 files, which is exactly the tracked source set. Add the file when something needs excluding, not before.
- 2026-08-29 CSharpier 1.3.0 also formats MSBuild XML, which was not expected. Accepted rather than ignored: the whole diff across seven `.csproj`/`.props` files is the removal of blank lines just inside `<Project>`, and an ignore list for it would be more configuration than the thing it buys.
- 2026-08-29 The tool manifest lives at `.config/dotnet-tools.json`, though the .NET 10 SDK's `dotnet new tool-manifest` now writes `dotnet-tools.json` at the repository root. `dotnet tool restore` resolves both; the `.config/` location keeps the root uncluttered. Verified restore from `.config/` after moving it.
- 2026-08-29 The Husky hooks are plain shell, not `task-runner.json` tasks. Both needed shell anyway: pre-push is a single `pwsh` line, and pre-commit needs `git add` after formatting, which the task runner has no concept of. `task-runner.json` is committed with an empty task list only because `dotnet husky install` recreates it on a fresh clone if it is absent.
- 2026-08-29 The pre-commit hook refuses a commit when a staged `.cs` file also has unstaged edits. It formats staged files and re-stages them with `git add`, and `git add` on a partially staged file sweeps the unstaged work into the commit as well - content nobody chose to commit. Refusing is a two-line guard; the stash-and-reapply dance that would handle it properly is not worth it for a case the slice driver never hits. Verified both paths: a fully staged mis-formatted file is fixed and re-staged, and adding an unstaged edit on top makes the hook exit 1.
- 2026-08-29 PowerShell 7 is documented as a hard prerequisite, and the `pre-push` hook gets no fallback to Windows PowerShell 5.1. Found by S01b's review: the hook calls `pwsh`, which is absent from an out-of-the-box Windows 11. A fallback would be worse than the failure, because 5.1 cannot run this tooling at all - `powershell.exe -Command "Import-Module ./tools/PortTools.psm1"` dies parsing `PortTools.psm1:387`, which uses null-conditional and ternary syntax that only PowerShell 7 has. The requirement predates the hook and was simply never written down; the hook is only what made it bite.
- 2026-08-29 Thread safety is asserted for `FuzzyRegex` (spec section 4, and the class doc) but was never asserted either way for `Match`. `Match` is **not** thread-safe, matching `System.Text.RegularExpressions.Match`, because `Groups` will be populated lazily. The gate for the pattern object is structural, not a concurrency test: a passing race test proves nothing, so the phase 2 slice that adds the first instance field to `FuzzyRegex` must add a reflection test asserting every instance field is `initonly`, which fires the moment a cache field appears - the actual failure mode, along with holding an `ArrayPool` rental on the instance instead of per-call. A multi-threaded stress test comparing against single-threaded results is a smoke test alongside it, never the gate. Not written in S02: every member throws `NotImplementedException`, so the field test would be vacuously green.
- 2026-08-29 Replacement templates speak **upstream's** language, not `Regex`'s: `\1`, `\g<name>`, `\n`, `\x41` and `\N{...}` are escapes and `$` is ordinary text. The two cannot both be honoured, because they disagree about `\` - measured against both engines, not reasoned: for the template `\n`, `regex.sub('.', r'\n', 'x')` gives a newline where `Regex.Replace("x", ".", @"\n")` gives a backslash followed by `n`. Choosing upstream's ports ~55 assertions in S02 verbatim (`test_sub_template_numeric_escape`, `test_symbolic_refs`, `test_basic_regex_sub`, `test_expand`) where choosing `Regex`'s would have made ~40 of them "not ported: different template language" - a permanent parity hole in the one area a fuzzy-regex user is most likely to have upstream code to move across. The cost accepted is that a .NET caller writing `$1` gets the literal text `$1`, which is exactly what upstream does. S01's `Match.Result` doc comment claimed `$1`/`${name}` and is corrected.
- 2026-08-29 `FuzzyRegex.Split` returns `string?[]`, not `string[]`, and puts `null` where a capturing group did not take part in a match. Upstream puts `None` there; the built-in `Regex.Split` instead omits the entry entirely, which both shortens the array and loses the difference between a group that matched empty and one that never ran. Verified against both engines: `regex.split('(x)|(1)', 'a1b')` is `['a', None, '1', 'b']` where `Regex.Split("a1b", "(x)|(1)")` is `["a", "1", "b"]`. Keeping upstream's shape ports all 8 affected assertions in `test_re_split` and `test_qualified_re_split` with identical positions and lengths.
- 2026-08-29 A `needs:<tag>` names the capability whose absence would make the test fail *and* that is least likely to land first; where a test needs two, the skip prose must name the combination, and **a slice must read the prose before un-skipping by tag alone**. Found in S02: five `Split` tests using `(?r)` and three using `\b`/`\m`/`\M` were tagged `needs:splitting`, so the slice delivering `Split` would have un-skipped tests that cannot pass without right-to-left search or word-boundary anchors. Retagged `right-to-left` and `anchors`. Two-capability tests were *not* retagged where both capabilities already have their own tests on the board (case-insensitive backreferences stay `ignore-case`; `\g<name>` in a template stays `substitution`), because nothing is hidden there - whereas `right-to-left` had no other test anywhere, so the mis-tag made the capability invisible to the status board and no slice would ever have been prompted to deliver it.
