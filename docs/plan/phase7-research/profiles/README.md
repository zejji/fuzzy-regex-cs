# Profiles, and the routes that produced them

`PROFILING.md` describes the routes; this folder holds the output of the ones that have actually
been run, so a later slice can read a real attribution instead of re-proving the tooling. The raw
captures (`.nettrace`, `.speedscope.json`, dotTrace snapshots) stay under `artifacts/`, which is
gitignored and regenerable; the derived text is committed here, which is what makes it evidence.

## 2026-09-19, S58: the EventPipe CPU route, proven on `WorkloadBenchmarks.FuzzyLong`

BenchmarkDotNet 0.15.8, `--job short`, Release, .NET 10.0.11, this machine. One real benchmark
rather than a sample, because the point of the probe is that the route survives contact with the
suite.

```powershell
# 1. Capture. The working directory matters: BDN walks up for a solution file and bench/ holds
#    FuzzyRegex.Benchmarks.slnx, which stops the walk before the .claude/worktrees copies.
Push-Location bench
dotnet run -c Release --project FuzzyRegex.Benchmarks --no-build -- `
    --job short --filter '*WorkloadBenchmarks.FuzzyLong*' -p EP `
    --artifacts ../artifacts/prof/S58
Pop-Location

# 2. Read. `-p EP` writes BOTH a .nettrace and a .speedscope.json; topN needs the .nettrace.
dotnet trace report artifacts/prof/S58/<name>.nettrace topN -n 30 --inclusive
dotnet trace report artifacts/prof/S58/<name>.nettrace topN -n 30
```

Cost: 28 s wall for the capture, under a second for each report. `dotnet-trace` 9.0.661903 was
already installed as a global tool.

Output: `2026-09-19-S58-FuzzyLong-topN-inclusive.txt` and `-exclusive.txt`, both committed here.
The `.speedscope.json` (604 KB, drag it onto https://speedscope.app for a flame graph) and the
`.nettrace` (2.4 MB) are in `artifacts/prof/S58/` and are regenerated by the commands above.

### What it blames

**Inclusive - the subsystem.** `Matcher.BasicMatch` at **95.88%**, entered through
`FuzzyRegex.Match` -> `Run` -> `DoMatch` -> `DoSimpleFuzzyMatch` -> `DoMatch2`, each of which is
above 96% inclusive and at or below 0.43% exclusive. So on a fuzzy scan of a megabyte, essentially
all the time is inside the matcher's main loop and none of it is in entry-point plumbing,
compilation or the BDN harness.

**Exclusive - the methods.** Three methods hold **84.8%** of CPU between them:

| Method | Exclusive |
|---|---:|
| `Matcher.FuzzyMatchString` | 30.29% |
| `Matcher.BasicMatch` | 30.1% |
| `Matcher.RetryFuzzyMatchString` | 24.45% |

Then a long tail an order of magnitude smaller: `ByteStack.PushSize` 2.12% and `PushNode` 1.94%,
`MatchState.PushFuzzyCounts` 1.68%, `SpanHelpers.ClearWithoutReferences` 1.19%,
`SpanHelpers.Memmove` 1.19%, `Array.Clear` 1.07%, `MatchState.ResetGuards` 0.42%.

Two things a later slice should take from that, neither of them acted on in S58, which changes no
`src/` file:

- **The inner loop is where the time is, and it is three methods wide.** S62 ("inner loop") has a
  target list of three rather than a search; S60's prefilter work is aimed at not entering
  `FuzzyMatchString`/`RetryFuzzyMatchString` so often in the first place.
- **The backtracking stack is ~6% and the clearing is ~3.5%** on this workload - real, but a tenth
  of the matcher itself. An optimisation there is not the first move.

One caveat, stated because a profile invites over-reading: this is **one** workload, a budget-1
fuzzy scan with the match at the very end of a megabyte. A literal scan or a `BESTMATCH` workload
will blame different methods, and the route above is exactly what to re-run before assuming
otherwise.

## 2026-09-19, S58: the allocation route, and exactly where it stops

`PROFILING.md` recommended a dotTrace Timeline snapshot read through the Rider MCP server for
allocation attribution, with `EventPipeProfiler(GcVerbose)` as the fallback. S58 ran both. **An
unattended session can capture an allocation profile and cannot read one.** The evidence:

**1. dotTrace captures.** `jetbrains.dottrace.globaltools 2026.2.2` installs as `dottrace`, and

```powershell
dottrace start --profiling-type=Timeline --timeout=30s `
    --save-to=artifacts/prof/S58/sizing-timeline.dtt `
    bench/FuzzyRegex.Benchmarks/bin/Release/net10.0/FuzzyRegex.Benchmarks.exe sizing
```

wrote a 54 MB snapshot - one `.dtt` header of 558 bytes plus 39 chunk files, the largest 41 MB.
Re-running over an existing snapshot is refused rather than overwritten: `The file ... already
exists`, exit code 1024. Target the `sizing` mode deliberately: it runs the engine in-process with
no BenchmarkDotNet child, so the snapshot is our code.

**2. Nothing here reads it.** `dottrace help` lists three commands - `start`, `attach`, `xmlfile`.
No `Reporter.exe` ships in the package (the only executables are `dottrace.exe`, the elevation
agent, the Dpa/Etw collectors and `xperf.exe`), and Reporter excludes Timeline snapshots anyway.
The Rider MCP server reported `ConnectionRefused` for the whole slice, so the one tool that reads
a Timeline as text was unavailable. The snapshot is a deliverable for the owner's IDE, not an
input to a slice.

**3. The GcVerbose fallback captures too, but only by attaching.** Letting `dotnet-trace` launch
the benchmark **deadlocks**:

```powershell
dotnet-trace collect --profile gc-verbose --output <out>.nettrace -- <bench.exe> -i --job short --filter '*WorkloadBenchmarks.FuzzyLong*'
```

left the child at 6.08 s of CPU and flat for eight minutes, the trace frozen at 161 KB and the
BenchmarkDotNet log empty. The same command minus `dotnet-trace` finished normally
(`FuzzyLong`, 157.0 ms, 992 B) - one variable different, so the tracer's launch path is the cause,
not `-i`. Attaching works:

```powershell
$bench = Start-Process <bench.exe> -PassThru -NoNewWindow -ArgumentList '-i','--job','medium','--filter','*WorkloadBenchmarks*',...
Start-Sleep -Seconds 3
dotnet-trace collect --process-id $bench.Id --profile gc-verbose --duration 00:00:00:25 --output <out>.nettrace
```

and produced a 2.7 MB trace. Note the sleep: a `--job short` single benchmark finishes in about
six seconds, which is faster than an attach, and dotnet-trace then fails with `Process with an Id
of <pid> is not running.` Attach to a run long enough to be attached to.

**4. And the capture cannot be attributed with the shipped tools.** `dotnet-trace convert
--format speedscope` succeeds, but what comes out is an evented, millisecond-weighted profile -
3 threads, 144 events, heaviest leaf `CPU_TIME` on all three - with no allocation weights
anywhere. `dotnet-trace report topN` runs over the same trace and ranks whatever stacks the GC
events happened to carry, which on this capture is `EventPipeMetadataGenerator.GenerateEventMetadata`
at 36%: harness noise, not engine allocation. Getting bytes per call site out of that `.nettrace`
means writing a TraceEvent program that reads `GCAllocationTick` payloads.

**Consequence, and it is the useful part.** For this engine the arithmetic route
`PROFILING.md` section 7 ends with is not the consolation prize, it is the answer:
`MemoryDiagnoser` gives exact bytes per operation, the allocation sites are few and named
(`MatchState.Create` at `src/FuzzyRegex/Engine/MatchState.cs:544-568` - a `GroupData[]` plus one
`GroupData` per group, a `RepeatData[]` plus one per repeat, then the stacks), and a benchmark
that varies group count or match count attributes the bytes by subtraction. A Phase 7 slice
should reach for a profiler only when that subtraction stops explaining the number - and when it
does, the honest options are a TraceEvent reader of our own or the owner opening a Timeline
snapshot in Rider.
