# S56 mutation triage - the engine

Survivor triage for the 59 `engine-rand-*` chunks S55 queued: random-partition windows over
`Engine/Matcher.cs`, `MatchState.cs`, `NodeCompiler.cs`, `Optimiser.cs`, `Iteration.cs`,
`ByteStack.cs`, `GuardList.cs`, `CharacterIndex.cs`, `MatchLimits.cs`, `Node.cs`,
`PatternObject.cs` and `Unicode/UnicodeCasing.cs`. The queue ran detached in the `stryker`
worktree on branch `stryker-queue` from 2026-09-18 to 2026-09-20 10:47-13:0x, Release build,
coverage analysis off, 2 runners, `FUZZYREGEX_TEST_THREADS=4`. Reports:
`.claude/worktrees/stryker/TestResults/stryker/<chunk>/reports/mutation-report.json`
(gitignored, so the numbers live here).

The parser, the API layer and `Engine/Substitution.cs` were S55's:
`docs/plan/mutation/2026-09-17-api-parser.md`.

## Result

A chunk's report counts mutants across whole files, but only the mutants inside that chunk's
character windows were ever in scope. Counted that way - mapping each mutant's line and column to
a character offset in the report's own embedded source, which is what
`python tools/stryker-inwindow-summary.py engine-rand` does, and which reproduces every table in
this document:

| Status | In-window mutants |
|---|---|
| Killed | 4,613 |
| Timeout (Stryker counts as detected) | 46 |
| RuntimeError (test host crashed) | 14 |
| **Survived** | **0** |
| CompileError (never ran - see below) | 533 |
| Ignored (all of them "block already covered") | 356 |

**4,673 mutants tested, 0 survivors.** Nothing needed a killing test and nothing is recorded as
an equivalent mutant, because nothing survived. Two things this does NOT say, both of which
matter more than the score:

- **No `NoCoverage` appears because coverage analysis is off**, not because every line is
  covered. With `coverage-analysis: off` Stryker runs the whole suite per mutant and never
  computes the per-test coverage that would let it report `NoCoverage`. Line coverage is S57's
  instrument, not this one.
- **533 in-window mutants never compiled**, so nothing was proven about the code they sit on.

A mutant counts as in-window only when its whole span is inside the window, which is Stryker's own
rule: taking any mutant whose first character is inside adds 165 that Stryker rejected with
"Removed by mutate filter" and 32 more CompileError, and changes nothing else. That is why the
Ignored column here is smaller than the reports' own, and it was found by review rather than
noticed (second pass, 2026-09-20).

## The 46 Timeouts: all remove a loop's way out

Stryker's `additional-timeout` is 30,000 ms above the suite's own baseline, so a Timeout here is
a test that genuinely stopped making progress, not a slow test. Every one of the 46 sits on the
statement or condition that lets a loop or a work-list walk finish. By method:

| Mutants | Method | What the mutation removes |
|---|---|---|
| 24 | `Optimiser.AddRepeatGuards` | the `NodeStatus.VisitedAg` mark, or the `!visited...` guard: a node is pushed again every time it is popped |
| 3 | `ByteStack.PushBlock` | the doubling in `newCapacity *= 2`, or the `_storage.Length == 0 ? 256` seed: capacity never reaches `newCount` |
| 3 | `PatternObject.GroupInfoAt`, `CallRefInfoAt`, `RepeatInfoAt` | the `List.Add` inside `while (list.Count <= n)`: the list never grows to the index asked for |
| 2 | `NodeCompiler.BuildBranch`, 2 `BuildSuccess`, 2 `Optimiser.SkipOneWayBranches` | the advance or the terminating branch of the same kind of walk |
| 1 each | `Iteration.Scan`, `Iteration.Split`, `MatchState.AdvancePastMatch`, `Matcher.BasicMatch`, `Matcher.CountOne`, `Matcher.DoExactMatch`, `NodeCompiler.BuildAny`, `NodeCompiler.SequenceMatchesOne`, `Optimiser.SetTestNode`, `Optimiser.UseNodes` | the `break`, the position advance, or the equality that ends the loop |

Method names here come from scanning back to the nearest declaration in the report's own embedded
source. The first scan's regex rejected nullable return types, so a mutant in
`internal static string?[] Split(...)` was attributed to the previous declaration, `Enumerate` -
found by the blind review, corrected above, and the only row in the engine's Timeout,
RuntimeError and CompileError attributions it changed.

Two were reproduced rather than reasoned about, with
`python tools/probes/s56-mutant-behaviour.py optimiser bytestack` (2026-09-20, this commit):

- `Optimiser.cs:186`, `node.Status |= NodeStatus.VisitedAg | ...` changed to `&=`
  (`engine-rand-51`): compiling `(a|b)*c` **still running after 60 s**; unmutated it answers in
  about 60 ms.
- `ByteStack.cs:113`, `newCapacity *= 2` changed to `/= 2` (`engine-rand-44`): matching
  `(?:abcdef){e<=3}` against 2,000 characters **still running after 60 s**; unmutated, about
  80 ms.

**Nothing is owed for these.** The slice asked for a per-test `[Timeout]` and an assertion
wherever a mutant hangs; `tests/FuzzyRegex.Tests/AssemblyTimeout.cs` already carries
`[assembly: TUnit.Core.Timeout(120_000)]`, added 2026-09-13 after a hang stalled the driver, so
every test in the suite is bounded and a hang lands as one named red test. What was missing was
anything that notices if that file goes away: `Gaps/Engine/HangBoundTests.cs` now asserts it, and
was watched failing with the bound changed to 600,000 ms before being committed.

## The 14 RuntimeErrors: `NodeCompiler` loses its instruction pointer

All 14 sit on the `args.Code += n` that advances the compiler's instruction pointer past the
opcode it has just built, in 14 different `Build*` functions (`BuildAtomic` twice - the
`--args.Code` and the statement that holds it - then `BuildBranch`, `BuildCallRef`,
`BuildConditional`, `BuildFuzzy`, `BuildGroup`, `BuildGroupCall`, `BuildGroupExists`,
`BuildLookaround`, `BuildRange`, `BuildRefGroup`, `BuildRepeat`, `BuildString`). Each mutation
turns the advance into a rewind (`-=`) or removes it, so the compiler re-reads code it has
already consumed.

All 14 carry `statusReason: "The test host crashed or became unreachable while testing this
mutant"`. **What crashed the host is not recorded anywhere**, and neither the JSON nor the
`run.log` names an exception - this note does not guess at one (S55 made that mistake with
"StackOverflowException" and its verifier caught it). What can be shown is that the mutants are
detected rather than equivalent, from
`python tools/probes/s56-mutant-behaviour.py string groupcall` (2026-09-20, this commit):

- `NodeCompiler.cs:1632` (`BuildString`, report line 1596), `args.Code += (int)(3 + length)`
  changed to `-=`: compiling `abcdef` throws `IndexOutOfRangeException` from
  `CompileArgs.get_Op()` in about 40 ms. Unmutated, it compiles and matches.
- `NodeCompiler.cs:1105` (`BuildGroupCall`, report line 1079), `args.Code += 2` changed to
  `-= 2`: `(?P<a>x)(?&a)` compiles but answers `Match("xx") = false` where the unmutated engine
  answers `true`.

A wrong answer and a thrown exception are both red tests. The host crash is what the same family
did to some other pattern in the 6,400-test suite; it is a detection either way, and no test is
owed.

## What never ran: 533 CompileError mutants

A mutant that does not compile is rolled back and scored `CompileError`. That is normal, but the
concentration is not: 123 of them are in `Matcher.cs::BasicMatch` and 62 in
`Matcher.cs::DoEnhancedFuzzyMatch`, the engine's two largest methods, followed by
`RetryFuzzyMatchStringFld` (21), `RetryFuzzyMatchGroupFld` (18), `RetryFuzzyMatchString` (16) and
`RetryFuzzyInsert` (16) - 91 methods in all.

`DoEnhancedFuzzyMatch`'s 62 were not judged individually. Every one of the 59 chunk logs shows

```
[..] An unidentified mutation in ...\Engine\Matcher.cs resulted in a compile error with id: CS0165,
     message: Use of unassigned local variable 'status'
[..] Safe Mode! Stryker will remove all mutations in DoEnhancedFuzzyMatch and mark them as 'compile error'.
```

One mutation Stryker could not attribute costs the whole method: safe mode drops every mutant in
it. The same happens in the parser to `CompileUnderVersion` (177 times across the queue),
`StringSet` and `ParseComment`. The compile-error location Stryker prints (`at 22896:12`) is a
line in its own generated file, not in `Matcher.cs`, which is 10,328 lines at the revision
those chunks mutated and 10,716 at HEAD - so the
mutation that triggers it cannot be identified from the logs alone.

**This is the honest limit of the 0-survivor claim**: about a tenth of the in-window mutants in these
files were never executed, and they are concentrated in exactly the methods Phase 7 will rewrite.
The upgrade path is a re-run of those windows with the mutator that provokes the CS0165 excluded,
so safe mode never fires and the remaining mutants are judged; that needs one bisect to find the
mutator and is left to the slice that next runs the queue.

## Summary

4,673 engine mutants tested, **0 survived**, 46 hangs and 14 host crashes each traced to a
removed loop bound or a lost instruction pointer, two of each reproduced by probe. The
qualifications, in the order they would bite a Phase 7 rewrite: 533 mutants in the engine's
largest methods never compiled (185 of them in `BasicMatch` and `DoEnhancedFuzzyMatch` alone);
1,048 lines of today's `Matcher.cs`, `PatternObject.cs`, `NodeCompiler.cs` and `FuzzyRegex.cs`
have never been mutated at all; and `NoCoverage` is not reported under these settings, so this
instrument says nothing about unreached code.
