# Deliberate differences from upstream mrab-regex

The running list of every place this port intentionally behaves differently from the pinned
upstream release, kept so that Phase 8's user documentation is written from a record rather than
from memory. **A slice that introduces or removes a deliberate difference appends to this file in
the same commit** (port-slice skill rule, 2026-09-14). Accidental differences are not listed here:
they are oracle divergences, and they are either fixed or pinned in
`tests/FuzzyRegex.OracleTests/ExpectedDivergences.cs` with a ledger entry in
`docs/plan/upstream-reports/LEDGER.md`.

Each entry: what differs, why, where decided, whether it is in the shipped code, and what a user
does to get upstream's behaviour if they can. "Owner" means the project owner decided it; the
DECISIONS.md date is the trail.

**The Status column is load-bearing.** `SHIPPED` means the behaviour is in `main` today, with the
slice in `docs/plan/slices/done/` or the decision already applied to the code. `PLANNED (Snn)`
means the difference has been designed and approved but the slice has not run, so the shipped code
still does what upstream does. Phase 8 must document only the SHIPPED rows as behaviour, and must
re-check every PLANNED row before writing about it.

## Defaults

| Difference | Why | Decided | Status | Upstream behaviour available? |
|---|---|---|---|---|
| **Version 1 is the default** (nested sets and set operations; full case-folding under `IgnoreCase`). ## API shape

| Difference | Why | Decided | Status | Upstream behaviour available? |
|---|---|---|---|---|
| **`Match` means upstream's `search`; upstream's anchored `match` is `MatchAtStart`** and `fullmatch` is `FullMatch`. | Naming upstream's `match` `Match` would silently give a .NET caller anchored behaviour, which is a trap no compiler catches. Static conveniences also take `(input, pattern, options)`, `Regex`'s argument order rather than upstream's. | DECISIONS 2026-08-29 (line 30) | SHIPPED (S01) | The mapping is documented; `MatchAtStart` is upstream's `match` exactly. |
| **`Regex`-shaped surface**: `FuzzyRegex`, `Match`, `Group`, `Capture` with `(Index, Length)`; `Matches`/`Split`/`Replace` naming. Also `expand` is `Match.Result`, `expandf` is `Match.ResultFormat`, `lastindex` is `Match.LastGroupNumber` with Python's `None` rendered as `-1`, and `lastgroup` is `Match.LastGroupName` with `None` rendered as `null`. | Idiomatic .NET; the design spec's public-API sketch. | Spec section "Public API sketch", S01; DECISIONS 2026-08-31 (line 164); PORTMAP:76-77, :276 | SHIPPED (S01, S24) | Python names are documented as a mapping in the API docs (Phase 8). |
| **Indices are UTF-16 code units**, not codepoints. This includes `FuzzyRegexParseException.Offset`, which differs from upstream's `error.pos` for a pattern holding a non-BMP character before the failure. | .NET strings are UTF-16; the ported tests translate every non-BMP expectation. `Source.Get` still returns whole codepoints, so the emitted bytecode is identical to upstream's. | Spec; DECISIONS 2026-08-30 (`Source` reads codepoints, counts `char`s); PORTMAP:666 | SHIPPED (S07) | No. Documented with an example for astral characters. |
| **Upstream's `pos`/`endpos` are reshaped to `beginning`/`length`.** `length` is a length in UTF-16 code units, not an end index, and `-1` means "the rest of the subject". Upstream's Python-slice reading of a negative `endpos` is not reproduced: `regex.search('abc', 0, -1)` searches `[0, 2)` where this port reads `-1` as "no limit". | .NET convention. The oracle recorder converts upstream's codepoint pair at the boundary, so a slip shows as a divergence rather than as silent agreement. | S01; DECISIONS 2026-09-12 (line 232) | SHIPPED (S01) | Pass an explicit length; the two conventions are documented side by side. |
| **`Split` spells "no limit" as `maxSplits = -1`**; upstream spells it `maxsplit=0` and reads a negative as "no splits". | .NET convention; the inversion is applied at the boundary only. | S01; `Iteration.cs` | SHIPPED (S01) | The mapping is documented. |
| **`Replace`'s `count` is inverted the same way**: here `-1` is "no limit" and `0` is "replace nothing"; upstream's `count=0` is "no limit" and a negative count replaces nothing. | The same .NET convention as `Split`, applied at the boundary only. The inversion has two ends, and the oracle consumer had to be taught both. | S01; DECISIONS 2026-09-01 (line 191); `Gaps/Substitution/SubstitutionRulesTests.cs` | SHIPPED (S24) | The mapping is documented. |
| **There is no `findall`.** Upstream's `findall` returns the *text* of the single capturing group when the pattern has exactly one, and a tuple of group texts when it has more. `Matches` returns `Match` objects, `EnumerateMatches` returns them lazily, and `Count` returns only a count. | `Matches` and `Count` were judged to cover every ported use, and a second result shape would duplicate the scan. The group-text rule is a trap worth documenting: `regex.findall(r'(\w\w\K\w\w)', 'abcdefgh')` is `['abcd', 'efgh']` while the matches are `'cd'` and `'gh'`. | S25; DECISIONS 2026-09-01 (line 199); PORTMAP:381 | SHIPPED (S25) | Read `Match.Groups[1].Value` over the `Matches` result, or over `EnumerateMatches` for a lazy projection (S53b). |
| **`Match.Groups` is an `IReadOnlyDictionary<string, Group>` as well as a list**, keyed by every group's name - or its number as text where it has none - in ascending group number. Upstream's dictionary view (`groupdict`) is the NAMED groups only. | The built-in `GroupCollection` has had exactly this face since .NET 5, and measuring it (`tools/probes/dotnet-groupcollection-dictionary.ps1`, .NET 10.0.10, 2026-09-16) shows it is total rather than named-only: the built-in's `Keys` for `(?<a>a)(b)(?<c>c)?` are `[0, 1, a, c]` (it numbers unnamed groups first); this port's are `[0, a, 2, c]` (measured 2026-09-16), the same set in Python's numbering, because group numbers here follow upstream's left-to-right order. `TryGetValue` is what the port gained from it - the non-throwing way to ask about a name the pattern may not have. Upstream's `groupdict` is a filter over this one. **The cost is a source break**: a type with two `IEnumerable<T>` faces makes `Groups.Select(...)` ambiguous, exactly as it is on the built-in collection. | S53b; owner decision 2026-09-16, `docs/plan/2026-09-16-unported-members-review.md` | SHIPPED (S53b) | `Groups.Values.Select(...)` restores the list projection; `groupdict` is the dictionary filtered to the non-numeric keys. |
| **A lazy walk times each STEP, where `Matches` times the whole scan.** `EnumerateMatches` and `EnumerateSplits` take a `timeout` like every other entry point, but the clock restarts before each match. Upstream's `finditer` scanner holds one state and so one budget for the walk. | Since S61 the walk holds one state too, so a per-walk budget would be natural - and it is still declined. Between two steps the time is the caller's, spent on whatever it does with a match, and a clock running across a `yield return` would time a walk out for work the library did not do. The built-in `Regex` draws the same line: on .NET 10.0.12, 2026-09-22, a 100 ms budget over five matches with 300 ms of caller work between each finishes without a timeout for `EnumerateMatches`, a `NextMatch` walk and a `foreach` over `Matches` (`tools/probes/bcl-lazy-walk-timeout.cs`). | S53b, reasoning restated by S61 | SHIPPED (S53b) | Use `Matches`, whose budget is the whole scan. |
| **`Split` returns `string?[]` and puts `null` where a capturing group did not take part.** Upstream puts `None` there; the built-in `Regex.Split` omits the entry entirely, which both shortens the array and loses the difference between a group that matched empty and one that never ran. | Keeping upstream's shape ports all eight affected assertions in `test_re_split` and `test_qualified_re_split` with identical positions and lengths. Measured against both engines: `regex.split('(x)|(1)', 'a1b')` is `['a', None, '1', 'b']` where `Regex.Split("a1b", "(x)|(1)")` is `["a", "1", "b"]`. | DECISIONS 2026-08-29 (line 48) | SHIPPED (S25) | This *is* upstream's behaviour; the surprise is for the .NET reader, so it is documented prominently. |
| **Replacement templates speak upstream's language** (`\1`, `\g<name>`, `\n`, `\x41`, `\N{...}`), not `Regex`'s `$1`. | Fidelity to upstream's `sub` semantics; `$` is ordinary text. | DECISIONS 2026-08-29 (line 47) | SHIPPED (S12, S24) | Not applicable; documented prominently because .NET users will expect `$1`. |
| **Exception mapping.** Upstream's `error` is `FuzzyRegexParseException`, and so are its bare `ValueError` rejections (the ASCII/LOCALE/UNICODE incompatibility, a cost equation with no digits). Upstream's `IndexError("unknown group")` from `Match.expand` becomes `ArgumentException`, while the same mistake in `sub` stays `FuzzyRegexParseException`, because upstream raises two different errors there too. The C compiler's `RuntimeError("invalid RE code")`, and every pattern on which upstream lets a Python internal error escape (`AttributeError`, `TypeError`, and `KeyError` from `V0\|V1`), become `NotSupportedException` or `ArgumentOutOfRangeException`. The 1 GB backtracking bound and a runaway recursion raise `InvalidOperationException`, never `OutOfMemoryException`, where upstream raises `MemoryError`. A matching timeout raises `System.Text.RegularExpressions.RegexMatchTimeoutException` where upstream raises `TimeoutError`. `\p{Infinity}` raises `OverflowException`, carrying Python's own message. | .NET exception idiom. `FuzzyRegexParseException` means upstream's `error` and nothing else, which is what the compile-parity corpus pins row by row. CA2201, S112 and MA0012 all reserve the memory exceptions for real allocation failures, so reusing one would make a genuine failure indistinguishable from this library's own limit. `RegexMatchTimeoutException` already carries the input, the pattern and the timeout, so a caller who handles `Regex` timeouts needs no new `catch`. | DECISIONS 2026-08-30 (lines 89, 117), 2026-08-31 (lines 121, 126, 128, 145, 152, 153), 2026-09-01 (line 193); PORTMAP:669, :670 | SHIPPED (S07-S16) | Not applicable; documented per method. |
| **`Match.allcaptures`, `allspans`, `groupdict` and `capturesdict` are not on the public surface, and will not be.** | The fifteen upstream lines that use them are already ported through `Groups` and `Group.Captures`, so unlike S04's named lists nothing is unwriteable without them. Owner decision D settled it for good. | DECISIONS 2026-08-30 (lines 68, 81); owner decision D, `docs/plan/2026-08-30-phase2-decisions.md` section 6; PORTMAP:653-655 | SHIPPED (decided S12) | Equivalent data through `Groups` and `Group.Captures`. |
| **The "unused keyword argument" message interpolates the name as written**, where upstream formats it with Python's `ascii()` repr: for a named list called `é` upstream says `unused keyword argument '\xe9'` and this port says `unused keyword argument 'é'`; for `a'b` upstream switches to double quotes and this port does not. ASCII names agree exactly. | `ascii()` is a Python terminal convention, not behaviour, and no test on either side pins the message, so implementing Python's `repr` for one string would be unverified code. | DECISIONS 2026-08-30; PORTMAP:667 | SHIPPED (S07) | Not applicable. |

Beyond the CPython object plumbing, the `concurrent` GIL dance, pickling and the pattern cache, this also drops `Pattern.scanner` and `regex.Scanner`, `Match.pos`, `endpos`, `string`, `re` and `regs`, `Match.detach_string`, `regex.template` and the `TEMPLATE`/`T` flag, the `LOCALE` and `DEBUG` flags as public options, `_compile`'s `ignore_unused`, `regex.compile`'s `cache_pattern`, `regex.prefixmatch`, and the `__copy__`/`__deepcopy__` protocol on patterns and matches. | No .NET meaning, covered by the runtime, or expressible through a member the port already has.
